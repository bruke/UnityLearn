# 08 - 资源热更常用方法

## 学习目标
- 能对比 Addressables 热更与自研 version.json 管线
- 会配远程 Catalog，并实现检查更新 → 下目录 → 下 Bundle
- 掌握全量远程、首包+远程、Content Update 三种常用落地方式

## 1. 和自研热更的关系

[热更新 / 05](/HotUpdate/05-资源热更流程) 描述的是：自己维护文件清单、CRC、下载器。Addressables 把清单换成 **Catalog**，把下载器换成 `DownloadDependenciesAsync`。

| | 自研 AB + version.json | Addressables |
|--|------------------------|--------------|
| 清单 | 自己生成 | catalog.json + hash |
| 差量 | 自己比哈希 | Catalog 指向新 Bundle 哈希 |
| 依赖 | 自己解析 manifest | Catalog 自动 |
| 适合 | 已有成熟管线、强定制灰度 | 新项目、以官方栈为主 |

**不要两套同时当主流程。** 用 Addressables 就以 Catalog 为准；自研清单容易和 Bundle 命名、Cache 抢同一批文件。

## 2. 热更最小链路（必会）

前提：

- 远程 Group 的 LoadPath 指向 CDN
- Settings 勾选 **Build Remote Catalog**
- 客户端能访问 `RemoteLoadPath` 下的 hash / json / bundle

运行时：

```csharp
using System.Collections.Generic;
using UnityEngine;
using UnityEngine.AddressableAssets;
using UnityEngine.ResourceManagement.AsyncOperations;

public static class AddressablesUpdater
{
    public static async void Run()
    {
        await Addressables.InitializeAsync().Task;

        AsyncOperationHandle<List<string>> check =
            Addressables.CheckForCatalogUpdates(false);
        List<string> catalogs = await check.Task;

        if (check.Status != AsyncOperationStatus.Succeeded)
        {
            Debug.LogError("检查 Catalog 失败，可走本地旧目录或提示重试");
            return;
        }

        if (catalogs != null && catalogs.Count > 0)
        {
            AsyncOperationHandle<List<IResourceLocator>> update =
                Addressables.UpdateCatalogs(catalogs, false);
            await update.Task;
            Addressables.Release(update);
        }

        Addressables.Release(check);

        // 示例：按 Label 拉取本章需要的远程依赖
        AsyncOperationHandle<long> sizeHandle =
            Addressables.GetDownloadSizeAsync("chapter1");
        long bytes = await sizeHandle.Task;
        Addressables.Release(sizeHandle);

        if (bytes > 0)
        {
            AsyncOperationHandle down =
                Addressables.DownloadDependenciesAsync("chapter1", true);
            await down.Task;
            Addressables.Release(down);
        }
    }
}
```

流程含义：

1. **InitializeAsync**：读当前 Locator（包内记录的远程 Catalog 地址）
2. **CheckForCatalogUpdates**：拉远程 `.hash`，判断 Catalog 是否变化
3. **UpdateCatalogs**：换成新 json，之后的 Key 解析用新表
4. **GetDownloadSizeAsync**：还缺多少字节（相对本地 Cache）
5. **DownloadDependenciesAsync**：把缺的 Bundle 写入 Cache

没有新 Catalog 时，不会无故重下全部资源。Bundle 文件名带哈希时，**没改动的包 URL 不变，客户端直接命中 Cache**。

## 3. 三种常用部署

### 3.1 几乎全远程

- 包内只留启动场景、Addressables 本地配置、远程 Catalog URL
- 几乎所有内容在 CDN
- 安装包最小；首次启动必须下载；无网不能玩

适合：强依赖运营、包体审核压力大。

### 3.2 首包 Local + 后续 Remote（最常用）

- Local：登录、新手关、核心 Shader、失败重试 UI
- Remote：后续关卡、皮肤、活动、高清包
- 无网至少能进游戏并看到「去更新」

Group 上分别选 Local / Remote 路径即可。

### 3.3 Content Update（已上线后的差量）

适用于：**App 版本不变**，只改 Addressable 资源。

1. 发版时保存 `addressables_content_state.bin`（分平台）
2. 改资源后：`Check for Content Update Restrictions` 处理静态组冲突
3. `Update a Previous Build`，把新的 catalog + 新 bundle 上传 **同一** RemoteLoadPath（或按你的版本目录策略）
4. 客户端仍走第 2 节的 Check / Update / Download

静态组（Cannot Change Post Release / Static Content）里的对象被改到，工具会要求你把变更挪到可更新组，否则应发新安装包。

操作顺序（编辑器菜单名随包版本略有差异）：

```
1. 发版当天：New Build → 保存
   ServerData/<平台>/addressables_content_state.bin
   （有的版本在 Library 或 AddressableAssetsData 下，以实际输出为准）
2. 把 content_state.bin 按平台归档进 Git 或制品库，丢了只能 New Build
3. 热更资源后：
   Groups → Tools → Check for Content Update Restrictions
4. 把必须改的条目从静态组挪到可更新组（或接受打新包）
5. Build → Update a Previous Build，选中那份 state
6. 把新的 catalog.hash / catalog.json 和新增、哈希变化的 bundle 上传到同一 LoadPath
```

Settings 建议：

- **Build Remote Catalog**：打开，否则客户端无法用 hash 发现更新
- **Disable Catalog Update on Startup**：打开。启动时自己调 `CheckForCatalogUpdates`，避免闪屏被官方自动更新卡住
- **Unique Bundle File Names**：打开。Bundle 文件名带哈希，没改的文件 URL 不变，缓存才能生效

## 4. CDN 目录策略

简单做法：每个 App 资源版本一个文件夹：

```
https://cdn.example.com/aa/1.2.0/Android/
    catalog_xxx.hash
    catalog_xxx.json
    *.bundle
```

注意：

- Catalog 里写的 Bundle URL 必须和实际上传位置一致
- 若用 `InternalIdTransformFunc` 做版本目录，Build 时可用占位域名
- 灰度：不同玩家指向不同 Catalog 根路径（渠道号、实验组）

强更 App（二进制变了）通常要 **New Build**，不要假设旧 Content State 仍适用。

## 5. 启动顺序建议

```
闪屏
  → 初始化 Addressables（可先不更新 Catalog，保证能显示本地 UI）
  → 检查 Catalog（失败则用缓存/包内目录，并提示）
  → 计算必更 Label 的下载量
  → 玩家确认后 DownloadDependencies
  → 进入游戏 / 加载热更 DLL（第 10 章）
```

不要在闪屏阶段同步 `WaitForCompletion` 拉完整游戏。

---

## 6. 与「整包替换 StreamingAssets」对比

部分项目热更是下载 zip 覆盖 StreamingAssets。和 Addressables Cache 是两条路。混用会导致两份 Bundle、路径错乱。选定 Addressables 后，远程资源应进入 **Unity Cache**，而不是自己解压到 StreamingAssets 再 `LoadFromFile`。
