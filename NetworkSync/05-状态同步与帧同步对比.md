# 05 - 状态同步与帧同步对比

## 学习目标
- 全面对比状态同步与帧同步
- 掌握选型依据
- 理解混合同步方案

---

## 1. 全面对比

### 1.1 核心对比
| 维度 | 状态同步 | 帧同步 |
|------|----------|--------|
| 同步内容 | 游戏状态（位置/属性） | 玩家指令（输入操作） |
| 权威方 | 服务器权威 | 客户端本地计算 |
| 服务器职责 | 计算所有逻辑 | 只转发指令 |
| 带宽占用 | 大（广播状态） | 小（只传指令） |
| 客户端负担 | 轻（只管表现） | 重（运行全部逻辑） |
| 逻辑确定性 | 不要求 | **必须确定** |
| 防作弊 | 强（服务器校验） | 弱（需额外校验） |
| 延迟敏感度 | 中 | 高 |
| 回放/观战 | 难 | 容易 |
| 服务器成本 | 高 | 低 |

### 1.2 带宽对比举例
```
一场 MOBA 战斗（10人，30 分钟）：

状态同步：
  每帧广播 10 个玩家的位置状态
  30Hz × 10人 × 30字节 = 9 KB/s/人

帧同步：
  每帧只广播 10 个玩家的指令
  30Hz × 10人 × 2字节 = 600 B/s/人

差距约 15 倍
```

## 2. 适用场景对照

### 2.1 状态同步适合
```
+ 大型世界（MMORPG）
+ 玩家数量多
+ 逻辑复杂（AI、任务、社交）
+ 服务器需要权威校验
+ 客户端性能有限（手机）

典型：原神、魔兽世界、剑侠情缘
```

### 2.2 帧同步适合
```
+ 实时竞技（MOBA、格斗、RTS）
+ 玩家数量少（≤ 20）
+ 逻辑可确定性
+ 需要精确回放
+ 需要低带宽（弱网）

典型：王者荣耀（早期）、星际争霸、格斗游戏
```

### 2.3 选型决策表
| 游戏类型 | 推荐方案 |
|----------|----------|
| MMORPG | 状态同步 |
| FPS | 状态同步 + 预测 |
| MOBA | 帧同步 或 状态同步 |
| 格斗 | 帧同步（回滚） |
| RTS | 帧同步 |
| SLG（回合） | 状态同步（TCP） |
| 棋牌 | 状态同步 |
| 赛车 | 状态同步 + 预测 |
| 休闲益智 | 状态同步 |

## 3. 为何 MOBA 多用帧同步

### 3.1 帧同步的优势在 MOBA 中
```
1. 带宽小：
   - 10 人实时对战，指令量极小
   - 弱网环境友好

2. 回放方便：
   - 电竞需要观战/复盘
   - 记录输入即可回放

3. 服务器便宜：
   - 服务器不跑逻辑，只转发
   - 成本大幅降低
```

### 3.2 MOBA 状态同步的挑战
```
1. 带宽大：
   - 10 人 + 小兵 + 塔的状态同步
   - 数据量很大

2. 延迟感知：
   - 每个操作等服务器确认
   - 竞技性受影响

3. 观战困难：
   - 需要记录所有状态
   - 数据量大
```

## 4. 帧同步 vs 状态同步的"反面案例"

### 4.1 状态同步在竞技游戏的问题
```
"王者荣耀为什么后来不用纯帧同步？"
  早期用帧同步（简化逻辑）
  后来部分玩法改成状态同步：
    - 大世界玩法（5v5 之外的）
    - 需要服务器权威的场景
    - 复杂技能逻辑（浮点、物理）

结论：没有绝对方案，按玩法混合
```

### 4.2 帧同步在大型世界的失败
```
"帧同步为什么不适合 MMORPG？"
  所有客户端要运行全部逻辑
  10万人在线 → 客户端也要跑10万人的逻辑
  → 不可能

结论：帧同步只适合"同一场对局"的小规模
```

## 5. 混合同步方案

### 5.1 为什么需要混合
```
大型游戏往往混合使用：
  - 大世界用状态同步
  - 竞技场/副本用帧同步
  - 不同玩法用不同方案
```

### 5.2 混合架构示例
```
MMORPG + 竞技场：

大世界（状态同步）：
  玩家移动、NPC、世界状态
  服务器权威 + AOI

竞技场/副本（帧同步）：
  5v5 对战
  帧同步指令 + 确定性逻辑
```

### 5.3 混合的挑战
```
1. 两套同步系统共存
   - 协议不同、状态不同

2. 切换问题
   - 大世界 → 竞技场的状态衔接
   - 玩家数据同步

3. 服务器架构复杂
   - 两种服务器（世界服 + 对局服）
```

---

## 6. 现代趋势

### 6.1 服务器权威 + 帧逻辑
```
现代竞技游戏：
  服务器也跑"确定性逻辑"（权威帧同步）
  客户端执行 → 服务器校验 → 不一致则修正

优势：
  - 保留帧同步的低带宽
  - 增强防作弊（服务器校验）
```

### 6.2 确定性状态同步
```
服务器用确定性逻辑计算状态
  所有客户端收到相同状态 → 完全一致
  用于对公平性要求极高的游戏（电竞）
```
